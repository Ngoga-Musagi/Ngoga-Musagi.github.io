1. The four-minute gap

The Kubernetes Horizontal Pod Autoscaler is a triumph of simplicity. You set a CPU target, it watches the metric, it adjusts the replica count. For workloads whose failure mode is “the box is too small,” HPA is genuinely all you need.

The problem is that most production incidents don’t start that way. They start in the logs:

  • A downstream dependency starts taking 3 seconds to answer. Your service’s connection pool fills up. Logs start emitting pool exhausted, waiting.
  • An upstream retries aggressively. Your error counter ticks. Logs emit upstream timeout: deadline exceeded, then circuit breaker open.
  • A bad config lands. A pod OOM-kills, restarts, OOM-kills again. OOMKilled appears in events.

None of these move CPU or memory in a useful way for several minutes. By the time the metric crosses a threshold, the incident is already underway, the on-call has been paged, and HPA arrives late.

The agentic autoscaler is a small, opinionated answer to that gap: let an operator read the same logs your humans read, correlate them with the metrics, and make a proactive, explainable scaling decision. Not a chatbot, not a sidecar — a real Kubernetes operator running a reconcile loop.

2. What “agentic” means in a control loop

The word agentic has had a hard year. Most of the time it’s code for “a chat UI that calls some tools.” That is not what this is.

In this project, agentic means a single thing: the reasoning step in the control loop is pluggable, and at least one of the implementations uses an LLM. The interface is one line:

// pkg/reasoning/agent.go
type Agent interface {
    Decide(ctx context.Context, signal fusion.FusedSignal) (ScaleDecision, error)
}

Four implementations live behind that interface:

  • RuleBasedAgent — deterministic, no network calls. The default and the safety net.
  • AnthropicAgent — calls the Claude API.
  • OpenAIAgent — calls OpenAI.
  • OllamaAgent — calls a self-hosted Ollama instance.

Switching providers is an environment variable (AI_PROVIDER=anthropic|openai|ollama|rules). The controller never imports a vendor SDK directly. If the cloud provider is down, mis-configured, rate-limited, or returns garbage, the loop falls back to the rule-based agent without redeploying anything. Vendor neutrality isn’t a slide here; it’s the architecture.

3. Architecture: six stages, one CRD

Every reconcile of an AgenticAutoscaler custom resource runs the same six-stage pipeline. Each stage is its own Go package, with a typed boundary in between, and not one of them has a hidden dependency on the next.

1Signalspkg/signals
2Fusionpkg/fusion
3Reasoningpkg/reasoning
4Policypkg/policy
5Scalerpkg/scaler
6Observabilitypkg/observability
↓ data flows left to right · observability records every decision regardless of outcome

The boundaries matter because they pin down what each layer is allowed to know. pkg/signals doesn’t know about Kubernetes — it’s pure Go that talks to Prometheus and a log source. pkg/fusion doesn’t know about LLMs — it just turns a snapshot into a typed structure with matched patterns and a severity score. pkg/reasoning doesn’t know about replica counts — it returns a ScaleDecision. pkg/policy is the only place that knows about HPA bounds and cooldowns. pkg/scaler is the only place that mutates a Deployment.

This is deliberate. When something goes wrong (and three things did, which we’ll get to), you can localize the bug to one of six packages and unit-test the fix without spinning up a cluster.

4. Signals: typed snapshots from Prometheus and logs

The first stage builds a SystemSnapshot from whatever sources the operator has been configured with:

// pkg/signals/snapshot.go
type SystemSnapshot struct {
    Timestamp time.Time
    Metrics   MetricSnapshot
    LogEntries []LogEntry
}

type MetricSnapshot struct {
    LatencyP99Ms   float64
    ErrorRatePct   float64
    CPUUtilPct     float64
    RequestsPerSec float64
    CustomMetrics  map[string]float64
}

The Prometheus collector (pkg/signals/prometheus.go) queries four canonical metrics by default — latency p99, error rate, CPU utilisation, and RPS — over a 2-minute window.

And here’s the part that turned out to matter more than I expected: every default query is overridable per-CR via a $TARGET token. If your service exposes its request count under a different metric name, you don’t fork the operator; you set:

spec:
  metrics:
    requestsPerSecond: 'sum(rate(http_request_duration_seconds_count{service="$TARGET"}[2m]))'
    cpuUtilization: '100 * avg(rate(container_cpu_usage_seconds_total{pod=~"$TARGET-.*"}[2m])) / avg(kube_pod_container_resource_requests{pod=~"$TARGET-.*",resource="cpu"})'

Two layers of leverage in one feature: any service can be onboarded without code changes, and you can measure CPU exactly the way HPA does (utilisation as a percentage of the CPU request) by overriding one string.

Logs are read by pkg/signals/logreader.go, which has two backends: Grafana Loki (HTTP query API) and Kafka (consumer group on a topic). Both return the same []LogEntry type. The choice is in the CR:

spec:
  logSource:
    type: loki
    loki:
      url: http://loki.monitoring:3100
      query: '{namespace="production",app="payment-service"} |= ""'

5. Fusion: turning log lines into patterns

Raw log lines aren’t a useful input to anything. pkg/fusion turns them into a small set of typed patterns and a severity score that a human (and a rule) can reason about.

The five patterns currently recognized (pkg/fusion/patterns.go):

PatternWhat triggers itSeverity
oom-killedAn OOMKilled event or restart linecritical
connection-pool-exhausted“pool exhausted,” “no available connections,” similar phrasinghigh
db-connection-failedDB driver errors, connection refused to the databasehigh
circuit-breaker-openOpen-circuit messages from common Go/Java/Node librarieshigh
upstream-timeoutDownstream call timeouts and deadline-exceeded linesmedium

The output of this stage is one struct:

// pkg/fusion/types.go
type FusedSignal struct {
    Snapshot        signals.SystemSnapshot
    MatchedPatterns []PatternMatch
    SeverityScore   float64
    Recommendation  string
}

That severity score is the single number a downstream rule or LLM can use to gauge “is this an actual incident, or just noise?” The full snapshot is still carried along so the reasoning stage can cite specific numbers when it explains a decision.

6. Reasoning: rules first, AI second

The rule-based agent is six ordered rules, each with a confidence value baked in. Whichever fires first wins, and only one fires per reconcile.

#TriggerActionConfidence
1oom-killed patternScale up 50%0.95
2connection-pool-exhausted AND p99 > 2 sScale up 50%0.90
3Error rate > 10%Scale up 30%0.80
4circuit-breaker-open patternScale up 30%0.70
5Severity = 0 AND CPU < 20% AND 15 min quietScale down to min+10.60
6(default)Hold—

Rule 5 is the underrated one. The system doesn’t scale down on a single quiet reconcile; it requires fifteen continuous minutes with no patterns and CPU under 20%. The cost of an unnecessary scale-up is a few minutes of extra capacity. The cost of a wrong scale-down is being short-handed when the next burst arrives. The rules treat these asymmetrically on purpose.

The LLM-backed agents (pkg/reasoning/anthropic.go, openai.go, ollama.go) receive the same FusedSignal rendered as a structured prompt. The model is asked to output a JSON ScaleDecision with three fields the system cares about:

type ScaleDecision struct {
    Action          string  // "scale_up" | "scale_down" | "hold"
    TargetReplicas  int32
    Confidence      float64
    Reason          string  // natural-language explanation
    Provider        string  // "rule-based" | "anthropic" | ...
    PatternsMatched []string
    // ... timestamps and audit fields
}

If the model fails — HTTP error, timeout, malformed JSON, anything — the controller logs the error and falls through to the rule-based agent for that reconcile. The cluster never ends up in a state where “the AI is down” means “the autoscaler is down.”

7. Why the AI refuses bad scaling decisions

This is the moment in the talk where the slide deck slows down.

While building this system, I ran two adversarial load tests to stress the AI’s judgement. Both produced the same result, and both were exactly what you’d hope a good engineer would do.

Test 1: inject 3-second latency on every request. The load generator pointed at payment-service with delayMs=3000. The latency histogram filled. p99 reached 4975 ms — well past the 2 s threshold.

The AI’s decision: hold. Its reason: “Despite extremely high p99 latency (4975ms), CPU is only 2.3% with no errors and a severity score of zero, suggesting the latency is not load-related.”

Test 2: inject 25% HTTP 500 responses. Error rate climbed: 11.8% → 14.9% → 20.7% → 25.6%.

The AI’s decision: hold. Its reason: “Despite a high HTTP error rate of 25.63%, CPU at 4% and p99 latency at 5ms suggest the errors are likely not load-related.”

Both rejections are correct. Artificial latency from /delay won’t be relieved by adding replicas — the bottleneck isn’t capacity. Injected 5xx from /status/500 won’t be relieved by adding replicas — the requests aren’t failing for capacity reasons. The model didn’t pattern-match on “number went up, scale up.” It looked at the shape of the incident.

This is the answer to the most common — and most reasonable — objection to putting LLMs in a control loop: they’ll hallucinate a scale-up and bankrupt me. In the same conversation those tests took place, the operator scaled out correctly the instant a genuine CPU-bound load drove utilisation past 70% of the CPU request. Good agentic behaviour, in infrastructure, looks like restraint.

8. Policy: nesting safely inside HPA

The single most important constraint on a new autoscaler is that it must not fight the existing one. The AgenticAutoscaler CRD makes this explicit with two coexistence modes:

  • Calibrated mode — the agentic autoscaler operates inside the HPA’s bounds. Its maxReplicas is always ≤ HPA’s maxReplicas, and its minReplicas is always ≥ HPA’s minReplicas. HPA stays in place as a safety net. This is the default for new deployments.
  • Owner mode — the agentic autoscaler takes full control. HPA is deleted or suspended. Reserved for deployments where the operator has been running calibrated for at least two weeks without incident.

pkg/policy/enforcer.go is the place where every ScaleDecision is bounds-checked, cooldown-checked, and HPA-checked. The package has read-only access to HPAs — it cannot modify or delete one. Belt and braces.

The cooldown is configurable per-CR (spec.cooldownSeconds, default 300 s in calibrated mode, 60 s in demos). After every scale event, the next non-hold decision is gated until the cooldown expires. pkg/policy/cooldown.go — one file, six tests.

9. Explainability: every decision has a sentence

The reason a platform team can’t adopt a black-box autoscaler isn’t that the box might be wrong — it’s that when it’s wrong, nobody can write the postmortem. The operator addresses this in two places.

The decision audit log. Every decision — hold, scale, dry-run, even errors — is appended to a ConfigMap in the operator’s namespace (pkg/observability/configmap_recorder.go). Each entry has a timestamp, the action, the old and new replica counts, the provider that produced it, the patterns matched, the confidence, and the full natural-language reason. kubectl get configmap decision-audit-log -o jsonpath='{.data.decisions}' is the entire interface.

Grafana annotations. Non-hold decisions are pushed to Grafana’s annotation API (pkg/observability/grafana.go) so they appear as red vertical lines on every dashboard. Hover one and you see the same reason text. The SRE’s mental model becomes: “the platform scaled at 14:32, and here’s the sentence explaining why.”

Scaled payment-service from 3 to 5 replicas. Reason: HTTP error rate exceeded 10% across two consecutive log windows with connection-pool-exhausted pattern matched 14 times. Confidence: 0.80. Provider: rule-based.

That sentence is the contract. Everything in the system exists to make it accurate.

10. The case study: API gateway timeout storm

The scenario is a realistic one: an API gateway service in front of three downstream microservices. One downstream begins to slow down. The gateway’s connection pool to that downstream fills up. Requests queue. Some time out. The HPA, watching CPU, sees nothing for the first several minutes — the CPU is fine, the gateway is mostly waiting on the network.

The agentic operator, meanwhile, has been reading the gateway’s logs. Inside two reconcile cycles it sees the connection-pool-exhausted pattern crossing three consecutive log windows. The fused signal’s severity score climbs above zero. The reasoning agent considers the combined picture — latency creeping up, errors creeping up, the named pattern asserting itself — and decides to scale out by 50%.

It posts a Grafana annotation: “Scaled due to timeout error rate exceeding threshold across 3 consecutive log windows, with connection-pool-exhausted pattern matched.”

Four minutes later, CPU on the original three pods finally crosses the HPA threshold — just as the new replicas are warming up. HPA would have scaled at exactly this moment. The agentic loop got there first by reading the signal humans always read first: the logs.

11. Three bugs you only find under load

The talk wouldn’t be honest without this section. While preparing the demo, I drove sustained traffic at the system and found three real bugs the unit tests don’t catch. All three are now in the issue tracker; one is a one-line fix; all three are worth talking about because they’re the kind of bug any operator built this way will eventually hit.

Bug 1 — Executor empty namespace

The controller correctly defaults the target namespace to the CR’s own namespace for reading the deployment. But when it passes the spec down to the scaler, it passes the raw spec, and the scaler reads spec.Namespace directly. If the CR didn’t set spec.namespace explicitly, that field is empty, and the scaler looks up the deployment in namespace "". The result: the AI’s scale-up decision is correct, the executor errors with Deployment.apps "payment-service" not found, replicas never move, and the reconcile silently retries with backoff. Symptom: nothing happens. Cause: empty string flowed through a boundary that should have defaulted.

The fix: one line in the controller, aa.Spec.Namespace = deployNS, before calling Execute. deployNS was already computed correctly a few lines earlier for the read path.

Bug 2 — The reconcile storm

Under load, the operator was reconciling every three seconds. Each reconcile collected signals, ran the AI, and updated status. The status update was triggering its own watch event, which enqueued the next reconcile immediately, which updated status, which… The 30-second requeue interval was set but had nothing to do because the queue never went empty.

The cost was real: roughly 20 LLM calls per minute, sustained, even when the system was healthy and holding. It also pushed the kind node container hard enough that it OOM-killed itself during one of the load tests — the data plane survived, but the control plane took the cluster API server down with it.

The fix is a predicate on the watch: ignore events whose only difference is a status field this controller wrote.

Bug 3 — Namespace RBAC for the management console

The operator ships an in-process web console (pkg/queryapi) on port 8090 with four tabs: Explore, Autoscalers, Onboard, and Load. The Onboard tab lets a platform engineer create an AgenticAutoscaler against any deployment in any namespace, with a dropdown of namespaces to pick from. That dropdown is populated by listing namespaces cluster-wide. The operator’s ServiceAccount has no such permission — intentionally, by the security rules in .claude/rules/security.md — so the dropdown stays empty and the controller logs namespaces is forbidden every forty seconds.

The fix is a small ClusterRole addition for get/list/watch on namespaces, scoped to the console’s read path only. The console writes through the existing per-CR RBAC; this only opens the listing.

The honest meta-point. All three bugs share a shape: a contract that the controller honored on the read path but didn’t honor on the write path. The fix in each case is to make the boundary explicit. This is what writing operators teaches you, and it’s a reasonable chunk of the talk.

12. Try it yourself

The whole thing is open source, Apache 2.0, and runs end-to-end on a single laptop. The bootstrap script creates a local kind cluster, installs Prometheus + Loki + Grafana, builds the operator, deploys a sample workload, and wires up the load generator — in one command.

git clone https://github.com/Ngoga-Musagi/agentic-autoscaler
cd agentic-autoscaler

# One command, fully self-contained
WITH_LOADGEN=1 bash hack/bootstrap.sh

# In a second terminal — port-forwards for the three UIs
bash hack/port-forward.sh

Then open three browser tabs:

  • http://localhost:8090 — the operator’s console. Drive load from the Load tab. Watch decisions on the Explore tab. Manage CRs from the Autoscalers tab.
  • http://localhost:3000 — Grafana. Open the “Agentic Autoscaler — Scaling Decisions” dashboard. Every scale event appears as a red vertical line. Hover one to read the reason.
  • http://localhost:9090 — Prometheus, in case you want to query the raw signals yourself.

If you want to onboard your own service instead of the sample, the Onboard tab is a form. Pick the deployment, set bounds, drop in custom PromQL if the service exposes non-standard metric names, and apply. No YAML required.

13. What’s next

The repository has a clear roadmap. The next three items, in order:

  1. OpenTelemetry traces in the audit path. Right now decisions are recorded to a ConfigMap and Grafana annotations. Adding a trace span per reconcile would let SREs follow a single scaling event from the metric query through the AI call through the deployment patch — useful for postmortems on the operator itself.
  2. More log patterns. The current five cover the high-confidence cases. Adding tls-handshake-timeout, dns-resolution-failed, and readiness-probe-failed would broaden the coverage without expanding the rule surface much.
  3. A community-shareable prompt library. The LLM prompt in pkg/reasoning/prompt.go is a single file and a single version. It would benefit from external scrutiny and from a small library of variants tuned for different workload classes (web tier, queue worker, batch).

If any of this resonates — or if you have a pattern in your logs that you wish your autoscaler could see — the repository accepts issues and pull requests. The codebase is small enough to read in an afternoon and modular enough that contributing to one stage doesn’t require understanding the others.

The goal of the project is not to ship the world’s best autoscaler. It’s to put a concrete, runnable answer to one question into the cloud-native ecosystem: what does it look like to bring AI into the Kubernetes control plane responsibly?

Built on Kubebuilder, Prometheus, Loki, KEDA, Helm, and Go. Vendor-neutral by construction. Reproducible end-to-end. Apache 2.0.

Thanks for reading. The repository is open — clone it, run the demo, file an issue.
